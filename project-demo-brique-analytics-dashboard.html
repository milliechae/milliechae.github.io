PAIN POINT

Every new pipeline meant filing a ticket and waiting on engineering.

Analysts understood the data better than anyone, but had no way to act on that understanding without routing every change through a backlog they didn't control.

  • Engineering bottleneck
    Even small changes to a pipeline required an engineer's time, turning simple requests into multi-day waits.
  • Opaque pipeline logic
    Once built, pipelines lived in code that non-technical analysts couldn't read, audit, or safely modify.
  • No visibility into pipeline health
    When something broke downstream, there was no easy way to see where in the pipeline the problem started.
✦ DESIGN CHALLENGE

How might we let analysts build and maintain complex data pipelines themselves, without needing to write or read code?

The goal was to translate pipeline logic into something visual and inspectable, so building a pipeline felt closer to sketching a process than writing a script.

RESEARCH

Understanding how analysts actually build pipelines.

Before designing the workflow builder, I spent time with analysts to understand how they thought through a pipeline from raw data to finished report, and where the current process broke down.

01

Analysts think in steps, not schemas.

People described their pipelines as a sequence of transformations — filter, then join, then aggregate — not as abstract data structures.

02

Debugging was the real bottleneck, not building.

Initial pipeline setup was often fine. What consistently ate time was figuring out where a pipeline had gone wrong once it did.

03

Reusability was invisible.

Teams frequently rebuilt near-identical pipeline steps from scratch because there was no way to find or reuse work someone else had already done.

✦ DESIGN HYPOTHESIS

Three hypotheses guided the redesign of the pipeline-building experience.

Research findings were translated into three assumptions that guided our design decisions before moving into interface exploration.

01  Represent pipelines as visual workflows

If pipeline steps are shown as connected nodes instead of code, analysts will be able to build and understand pipelines without engineering support.

02  Surface data health at every step

If analysts can preview data at each node, debugging will move from guesswork to direct inspection.

03  Make components reusable across teams

If pipeline steps can be saved and shared, teams will stop rebuilding the same logic from scratch.

Design Solution

Rather than exposing pipeline logic as code, the platform was designed around a visual workflow canvas — making construction, inspection, and reuse all part of the same continuous experience.

A drag-and-drop workflow canvas, not a code editor.

Analysts assemble pipelines by connecting steps on a canvas, translating the "filter, then join, then aggregate" mental model directly into the interface.

Node-level data preview at every step.

Every node in the pipeline can be inspected on its own, so when something breaks, analysts can see exactly which step introduced the problem instead of debugging the pipeline end to end.

Reusable, shareable pipeline components.

Common steps can be saved as reusable components and shared across teams, cutting down on duplicated work and keeping pipeline logic consistent org-wide.

🧱 Build once, reuse everywhere.

Saved components live in a shared library, with an auto-suggestion feature that surfaces existing steps as analysts build, so teams stop reinventing logic that already exists elsewhere in the org.

Impact: Fewer tickets, faster pipelines.

By moving pipeline construction out of engineering's queue and into analysts' hands, the platform shortened the distance between having a data question and getting an answer, cutting down on both request backlogs and debugging time.

Reflection

The platform could have exposed every possible transformation from day one. What actually earned analysts' trust was letting them see, at every step, exactly what the pipeline was doing — before it did anything clever.
